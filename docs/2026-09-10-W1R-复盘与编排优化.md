# Sol Advisor 编排复盘与优化建议

> 日期：2026-09-11
> 主案例：12306 HTTP API MVP 的 W1-R 控制面正确性修复（Codex session `01a08a28-bdbe-7b52-9c53-a0e8b4dcc132`）
> 结论：保留 Sol Advisor 的“实施—主验—独立终审”分离；优化送审前验证、同类缺陷处理和 `rethink` 分流。本文是后续插件修改的决策入口，不代表这些规则已经落地。

## 1. 范围、方法与口径

本复盘读取了历史 session 中的正式 reviewer verdict、Terra 修复交接、主验记录、Goal 运行计时和任务书，并复核了当前 Sol Advisor 的角色合同。没有在历史提交上重跑全部代码，代码层面的结论以当时记录的可复现证据为准。

“同一轮次”指同一冻结目标、同一验收门、失败后沿同一修正线继续，并由不同 fresh reviewer 重新审核。每次修复都会改变候选字节，因此不表示审查的是同一个 diff。

“被拒”指正式 `fix-first` 或 `rethink`，但不等价于“Terra 又写错一次”。每个 verdict 都应归入以下一种原因：

| 类别 | 定义 | 正确后续动作 |
| --- | --- | --- |
| 实现缺陷 | 生产行为违反合同，或可复现地走错安全/业务路径 | 交回实施者修复，主验后 fresh review |
| 测试或证据缺陷 | 生产代码已正确，但测试没有执行实际路径、证据无法证明合同、或全量门不稳定 | 修测试/证据或修实际竞态；不把它泛称为业务实现失败 |
| 合同或环境阻塞 | 现有白名单、验收条件、平台能力或威胁模型彼此冲突 | 主 Agent 裁定范围或架构；不能让 Terra 在旧任务书里硬修 |
| 评审无效 | reviewer 修改字节、命令纪律违规、审中候选发生变化、路由/隔离无法确认 | 作废 verdict，固定候选后重审 |

历史 session 的 verdict 格式并不完全统一，例如 `VERDICT: fix-first`、`VERDICT fix-first` 和中文说明并存。因此早期按字符串统计的次数可能偏低；本文只以每个 session 中可确认的正式 reviewer 返回为依据。

## 2. 同一验收门反复被拒的案例

### 2.1 W1-R：五次 `fix-first`，最终诚实停在 `W1_PARTIAL`

- Goal：修复 W1 控制面的 A–G 性质；一个 Terra 实施，主 Agent 验证，fresh Sol 终审。
- 主动运行时间：6 小时 41 分；最终全量测试为 114，不是中途快照的 107。
- 结果：Sol #1–#5 均为 `fix-first`；在用户加入类级清扫和 matrix 收敛规则后，最后没有再开 Sol，而是保留 `W1_PARTIAL`。C7 admitted-crash/finalize 幂等性仍未证，安装场景还观察到重复本地 call 文件。

主要拒绝链：

1. Sol #1 发现合法随机 requestId 被公开扫描误拦、status 隐藏较新的未决 marker、stop/acceptance 身份校验不足、提交谓词未在同一受保护边界内重读等问题。
2. Sol #2 发现 grant 授权折返、敏感字段扫描、campaign/request/domain 身份和 corrupt-tail 处理仍存在旁路。
3. Sol #3 发现 request/grant/claim 的耐久身份、mailbox 父目录与最终文件的 symlink/no-follow、测试域漂移等问题。
4. Sol #4 发现 grantId 未进入 intent identity、公开 transition 仍可绕过 claim、权威读取仍是检查后按路径读取等问题。
5. Sol #5 将剩余问题归为既有类的残余实例：完整身份绑定、mailbox 边界、父目录/no-follow、畸形 durable authority、corrupt-tail 和数组安全投影。

根因不是单一模型能力问题：

- 任务书用 A–G 定义的是跨入口性质，实施与修复却按 finding 的发生点推进；run、Core、status、stop、恢复、mailbox 的消费者没有同时收口。
- 首个 reviewer 启动前，Goal 已运行约 2 小时 38 分钟；六个多小时不应全算作终审造成的返工。
- 折返/fold 路径在开工基线已有，不能笼统写成“修复轮新增机制”；准确说法是修复过程中修改了既有折返路径并引入新的交互遗漏。
- 同一 Terra 有一次续跑只返回风险说明，之后在新上下文继续；不是实施者换人。长会话导致全局性质在当轮 finding 清单面前被削弱，这是合理怀疑，但没有足够证据证明它是首要根因。
- Matrix 建立后，主验仍查到 corrupt-tail 和 marker 投影的两处残余。因此 matrix 能提高可追溯性，不能单独证明已收口。

### 2.2 W1-C 首轮：三次 `fix-first` 后按上限停止

- 对话：`01a08c71-c5fb-7052-8930-944c53835002`，`CHECK-W1C`。
- 主动运行时间：1 小时 47 分。
- 链路：`w1c_review_1`、`w1c_review_2`、`w1c_review_3` 都是 `fix-first`；原 Terra 处理修复；第三次后依任务书标为 `BATCH_BLOCKED`。后续用户明确重开，才产生另一个修正周期。

三轮集中揭示：stop transaction、marker 快照、owner capability、duplicate/restore 和 Core 消费者并不是独立问题。第一次修了原子性，第二次发现 capability 可逸出和复用，第三次仍有 `RELEASED` capability、未决 marker 下的 stop、foreign campaign 污染和 duplicate 发布问题。

这说明对共享原语，不能把“封住 reviewer 指出的入口”当作完成。第一轮实现前应先列出：能力的创建者、持有者、传递边界、失效条件、所有调用者与错误出口。

### 2.3 匿名查询 Phase B：owner 生命周期的连续遗漏

- 对话：`01a06bed-1f7f-7661-9242-1ef35405171f`。
- 主动运行时间：4 小时 20 分。
- 同一 Phase B 收敛线中，`anonymous_owner_final_sol`、Sol #5、#6、#7、#8 均出现 `fix-first`；中间一次 `ship` 因 reviewer 自身命令纪律问题被作废。

先后发现的不是同一个 if 写错，而是同一 owner 生命周期的不同阶段：invalid handoff 前未进入 finally、成功发布先于 release、stale reclaim 双 owner、Attempt 时钟与 lease 时钟不一致、时钟回拨与 TTL 溢出。此类问题需要状态机和转换表，而不是逐条补 try/finally。

### 2.4 FSU：三次 `fix-first` 后获得 `ship`

- 对话：`019fdc9f-476c-70e0-b23c-67d5a8de772c`。
- 主动运行时间：2 小时 44 分。
- 链路：`review_fsu` → `review_fsu_final` → `review_fsu_final2` 均为 `fix-first`，随后 `review_fsu_final3` 为 `ship`。

第一次发现重启后可绕过目录同步；第二次发现 proof 可以由普通 hook 伪造，且 WAL inode 在检查和打开之间可更换；第三次发现不可信 no-op hook 写出的 PASS sidecar 能在重启后变成激活证据。最终修复把每次 open 固定为 `PENDING → 当前目录 helper → dev+ino 复核 → PASS`，并把生产 hook 来源与 proof 绑定。

这个案例说明“持续化 PASS 记录”本身就是权限/来源问题；只验证结果文件存在不够。

### 2.5 HOST-4：前三次属于不同性质，第三次不是 HOST-4 代码缺陷

- 同一对话：`019fdc9f-476c-70e0-b23c-67d5a8de772c`。
- 链路：`review_host4`、`review_host4_final`、`review_host4_final2` 均为 `fix-first`。

前两次分别发现 wrapper admission 可被直调/import 绕过、TaskSpace cleanup 必须要求精确 `{done:true}`、证据目录可覆盖/合并。第三次 reviewer 已确认 HOST-4 的入口、证据和 fail-closed 结论正确，但全量回归在既有 coordinator timing 用例上不稳定，因此不能验收。

复盘时应把第三次归为“全量测试/异步竞态未闭合”，而不是“HOST-4 又实现错误”。

### 2.6 Stage3c-C：生产代码与证明代码分离

- 对话：`019ffbd4-f1da-7ca0-bc91-d3dbf3e7d36c`。
- 主动运行时间：14 小时 31 分。
- 链路：`stage3c_c_final_review`、`stage3c_c_rereview`、`stage3c_c_final_ship_review` 均为 `fix-first`。

第一次是生产缺陷：capture-finalize 抛错会遮蔽已耐久的 `SUBMIT_UNKNOWN` 或 `CONFIRMED_PENDING_PAYMENT`。后两次 reviewer 明确认可生产 tail 的严格 readback 和 outcome 投影，只拒绝测试：静态 denylist、调用次数和字符串顺序无法证明“恰好一次 readback、没有 owner/action 重入”。

结论：静态测试是辅助门，不是语义证明。若验证目标是调用边界与耐久终态，应构造可观察的行为注入或端到端 harness。

### 2.7 V1.9 P1：三次局部修补后应当 `rethink`

- 对话：`019ff55d-1a08-7533-903a-43ce58e5446a`。
- 主动运行时间：43 小时 4 分。
- P1 先后处理 issuer factory、raw builder export 和 JS 私有闭包；`p1_boundary_final_sol` 最终给出 `rethink`。

核心证据是：调用者可读/改 grant A 的 bytes，只改 grantId 成 B，再直接加载 native addon 写入 B；JS 层隐藏 factory 无法证明 native writer 的 issuer provenance。

这类 verdict 应立即转为架构决策：需要 native 强制的 opaque issuer/high-level issuance boundary 或认证记录。继续在 JS export 上局部修补只会增加轮次。

## 3. 整个 session 多次被拒，但不属于同一轮次的情况

| 对话或阶段 | 主要模式 | 复盘结论 |
| --- | --- | --- |
| R4→R6 MVP 接线，`01a047e6-…` | R4 原周期两次拒绝后按规则停止；用户明确重开后才完成 R4，R5 又遇到白名单冲突 | 重开验收门要作为新周期单独计数；开工前检查验收要求与白名单能否同时满足 |
| HTTP Skill，`01a03006-…` | Stage2B 三次、Stage2C 四次、Stage3A/3B 各三次局部拒绝 | 单元测试与真实 transport/redaction、Controller、Candidate、gate 来源脱节；应先跑一条贯穿真实模块的离线链 |
| HTTP PoC 长任务，`019ffbd4-…` | 协议采集逐步扩展为 retry、崩溃安全和 coordinator 工程 | 产品目标变化时应关闭旧阶段、重估工作量，不能把新增架构不断塞进同一个 Goal |
| V1.9 超长任务，`019ff55d-…` | native transport、恢复证明、同 UID 写入边界逐层扩展 | 先验证运行环境与威胁模型可行性；架构缺口必须早于大量实现暴露 |
| V1.8 合并前准备，`019fe6d4-…` | AccountBinding 跨页面、生产 bootstrap、Worker 轮换等到集成才发现 | 先验证生产入口、真实 DTO 与授权依赖；fixture 不可代替接口接线 |
| V1.9 Direct 验收，`01a00fa0-…` | 最终 `rethink` 来自验收条件冲突：要求 stopped-only 测试，同时禁止停止健康保活 | 这是合同/环境阻塞，主 Agent 应裁定；继续派 Terra 不会解决 |

## 4. 是否保留 Sol Advisor

建议保留，保留的是以下责任分离：

```text
Terra 实施 → 主 Agent 独立验证 → fresh Sol 审核与最终 verdict
```

这些历史审核抓到了实质问题：错误 ACK、Candidate/Campaign 错绑、重复发布、正常链路不可执行、native writer 来源无法证明、持久状态错误投影。取消独立审核，只会让其中一部分问题更早被标记完成。

但这些样本是专门挑出的失败会话，不提供“无独立审核”“换实施模型”或“使用 tester”的对照。因此不能据此断言 Terra 普遍不可靠、reviewer 越多越好，或四 Agent 必然节省时间。

当前插件的 `solo / delegate / audit / full` 四种路由应保留。普通、边界明确的改动继续默认 `solo` 或 `delegate`；共享持久状态、权限、跨模块接线、不可逆业务边界才使用 `full`。

最需要改变的是第二次出现同类遗漏后的动作：不应原样重复“finding → 修 → 全测 → fresh review”。主 Agent 必须先判断是消费者清单漏了、机制设计不成立、测试没有跑真实路径、合同/环境冲突，还是 reviewer/候选无效。

## 5. 对原优化方案的评估

### 应直接采用

| 原提议 | 结论 | 落地边界 |
| --- | --- | --- |
| finding → 类 → 相关站点清扫 | 采用 | 仅覆盖合同涉及、实际可达且在授权范围内的消费者；不是全仓库无限扫描 |
| invariant-matrix | 采用 | 每格记录生产入口、反例、证据和 N/A 理由；用于追踪，不能充当完成证明 |
| 每个负例配相邻正例 | 采用 | 适用于输入验证、恢复、fail-closed 逻辑，避免修复误伤合法路径 |
| Terra diff 自审与“未验证项” | 采用 | 报告需指向实际文件、函数、命令和输出；自述不能替代主验 |
| reviewer 标注合同条目、类别和故障场景 | 强烈采用 | 还需明确影响、复现或静态推导证据、归属类别和 required next action |
| 主验机械核对报告与代码 | 采用 | 包括 diff、入口、测试实际覆盖对象和证据产物，不只 grep 文本 |

### 需要修改后采用

| 原提议 | 问题 | 修改后的规则 |
| --- | --- | --- |
| “已有类残余”一轮清扫后即可收口为 `PARTIAL` 或 `ACCEPTED` | 既有类的残余仍可能是阻塞性安全问题；W1-R matrix 后仍发现两处残余 | 连续两次同类遗漏触发主 Agent 诊断与类级清扫；预算耗尽可收口为 `PARTIAL`，`ACCEPTED` 仍须满足原冻结验收门和最新 fresh `ship` |
| `rg` 作为收口证据 | 只能证明某类调用写法是否仍存在，不能证明竞态、身份来源或状态语义 | 作为 inventory 辅证；每个高风险类别仍需行为反例或明确的等价证明 |
| 每条性质至少一个独立反例 | 机械填表会制造低价值测试 | 聚焦跨机制边界和高风险性质；预期来自合同，允许读实现以设计可执行 hook |
| 独立测试 Terra 完全不看实施测试 | 第一次测试设计可隔离，但后续修复必须能读取失败证据；只隔离文件不等于独立 | 独立 tester 先从合同设计预期和测试，再检查代码；实施者可读取失败测试；tester 只拥有明确的独立验收测试文件，不独占整个 `tests/**` |
| 四 Agent 默认化 | 没有对照数据证明节省总成本 | 先对 2–3 个高风险任务试点，记录有效拒绝轮数、逃逸缺陷、主动时间、token、重复验证成本 |

### 不应按现稿采用

“对用户自己的状态目录有写权限的进程本来能改 journal，因此 no-follow 只是边际硬化”这个例子过强。应区分正常并发/崩溃、经支持接口触及状态、以及任意同 UID 恶意写者完全控制目录。路径跳转还可能指向状态根之外，不能仅以 journal 是否可改来判定不阻塞。

正确做法是开工前冻结威胁模型。若明确不防任意同 UID 恶意写者，reviewer 不能临时要求升级为独立 UID 平台；已经承诺的路径、损坏处理和 containment 保证也不能事后统一降级。

## 6. 建议的最小落地版本

先修改编排规则，不立刻新增 tester 角色或改变默认路由。

1. 开工时形成小型验收包：目标、关键性质、相关生产入口、允许的故障/攻击模型、排除项、白名单、接受条件。
2. 首轮实施必须证明一条真实模块链路：从公开入口到预期输出，只替换网络等外部边界；禁止用跨模块 mock 伪造接线成功。
3. reviewer 的 finding 固定为结构化字段：合同引用、类别、影响、证据、相关消费者、归属与 next action。
4. 第二次同类遗漏后，主 Agent 必须写出诊断结论，再决定类级清扫、重新设计、补真实接线测试、修改验收条件，或作废评审。
5. 每次正式 review 审核稳定候选。审查期间发生代码变更，旧 verdict 和证据立即作废；不能在审中修完后继续使用同一 review。
6. 独立 tester 只在共享持久状态、权限、跨模块接线等高风险任务试点，并记录成本和实际收益。
